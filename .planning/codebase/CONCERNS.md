4. **Run build:**
   - Node.js: `cd napi && npm run build` or `napi build`
   - Python: pyo3 generation happens automatically via build.rs in pyo3 crate
5. **Commit both Rust source AND the generated artifacts** (they will be regenerated, but git needs the snapshot)

**Per-crate opt-outs (if needed):**
- Add to crate's `Cargo.toml`: `[lints] workspace = true` followed by `unsafe_code = "allow"` override

- This currently has NOT been needed; all crypto is delegated to upstream crates

**Mitigation:**
- New cryptographic code (e.g., silent payment scalar reductions, EIP-712 hashing) should NOT use unsafe
- If FFI is required, isolate it in a separate opt-in crate or upstream contribution
- Code review should flag any `unsafe` blocks as high-priority review

## Signed vs. Unsigned Scalar Reduction (Crypto Hazard)

**Context:**
- File: Likely in `crates/chia-sdk-types/src/` (search for `mod_by_group_order` — currently NO direct definition found, it's likely in upstream `chia-bls`)
- Current SDK behavior: Synthetic key offset arithmetic may be using signed reduction for backward compatibility
- CHIP-0057 (silent payments) protocol: Requires UNSIGNED scalar reduction for cryptographic security

**The hazard:**
- Synthetic keys (curried into standard puzzle) use *signed* mod_by_group_order for historical reasons
- Silent payments must compute input_hash, output_tweak, and label_scalar using *unsigned* reduction
- If code mixes signed and unsigned reduction silently, the resulting payment amounts are cryptographically undetectable

**Why this matters:**
- Standard Chia wallet key: `private_key` → synthetic_key = sha256(private_key || hidden_puzzle_hash) mod order
- CHIP-0057 receive-side key: input_hash = sha256(public_key || output_index) mod order (UNSIGNED)
- If input_hash uses signed modular reduction but sender uses unsigned, payment detection fails

**Current state:**
- SDK does NOT yet implement CHIP-0057; this is scaffolding stage
- No direct `mod_by_group_order` function found in SDK source (upstream `chia-bls` handles it)
- CHIP-0037 work (EIP-712 message layer) is recent; needs review for any modular arithmetic

**Mitigations:**
1. **Type-level separation:** Create distinct newtypes for signed vs. unsigned scalars
   - `SignedScalar(Fr)` for synthetic key offsets
   - `UnsignedScalar(Fr)` for silent payment derivation
   - Compiler prevents mixing at compile time
2. **Documentation:** Mark clearly in silent payment code: "All scalars here are UNSIGNED mod group order"
3. **Cryptographic test vectors:** Validate output_tweak and input_hash against CHIP-0057 reference implementations
4. **Code review:** Require cryptography expert review on any PR touching silent payment scalar math

## CAT2 Receive-Side Detection Gap

**Current state:**
- File: `crates/chia-sdk-driver/src/primitives/cat.rs` — CAT2 send-side fully implemented
- CAT2 receive-side detection requires extracting inner puzzle hash from CAT-wrapped outputs

**The gap:**
- **Senders:** Can construct CAT2 coins using `Cat::issue_with_coin` or `Cat::issue_with_key`
- **Receivers:** Cannot automatically detect incoming CAT2 coins without indexer support
  - CAT wraps an inner puzzle (usually standard puzzle for XCH-equivalent token)
  - The inner puzzle hash is buried inside CAT args; indexer must parse it
  - Light wallets (CHIP-0058) will have this, but it's NOT defined yet

**Downstream:** 
- Wallet UI cannot show "you received 100 TOKEN" until CHIP-0058 light protocol is deployed
- Workaround: Manually track CAT tail hashes and inner puzzle hashes in wallet state

**Impact on CHIP-0057:**
- Silent payments + CAT2 = receive-side detection for silent CATs
- Still requires indexer to extract inner puzzle hash from CAT args
- Design concern: Silent payment detection algorithm must account for CAT wrapping

**Mitigations:**
1. **Document:** In any CAT2-related API, note "CAT2 send-side only; receive-side detection awaits CHIP-0058"
2. **Design CAT2 Silent Payment API:**
   - Accept `CAT_TAIL_HASH` and expected inner puzzle hash as params
   - Verify incoming CATs match expected tail and inner puzzle
   - Avoid indexing; assume caller provides this metadata
3. **Future:** Once CHIP-0058 is spec'd, indexer support will become clear

## Synthetic Keys vs. Raw Keys Confusion

**Definitions:**
- **Raw wallet key:** Private/public key pair from HD wallet derivation (BIP44/BIP32)
- **Synthetic key:** `sha256(public_key || hidden_puzzle_hash) mod group_order` — curried into standard puzzle
- Standard puzzle hash = standard_puzzle(synthetic_key)

**Current SDK usage:**
- File: `crates/chia-sdk-driver/src/layers/standard_layer.rs` line 19-25
- `StandardLayer::new(synthetic_key: PublicKey)` — Takes synthetic key, not raw key
- All condition signatures are generated with synthetic key
- If you have only the raw key, you must compute synthetic_key first

**Common mistake pattern:**
```rust
// WRONG: signing with raw key instead of synthetic key
let signature = raw_key.sign(message)?;  // Will fail signature validation

// CORRECT: must use synthetic key
let synthetic_key = compute_synthetic_key(raw_key, hidden_puzzle_hash)?;
let signature = synthetic_key.sign(message)?;
```

**Silent payments implication:**
- CHIP-0057 silent payment output generation uses synthetic key
- Sender must NOT accidentally use raw key to generate output_tweak
- Receiver must NOT accidentally use raw key to detect payments

**Mitigations:**
1. **Naming convention:** Enforce strict naming:
   - `raw_pk` / `raw_sk` for wallet keys
   - `synthetic_pk` / `synthetic_sk` for curried keys
   - `inner_pk` / `inner_sk` for action layer keys (different scope)
2. **Type safety:** Create `RawPublicKey` and `SyntheticPublicKey` newtypes, prevent implicit conversion
3. **Documentation:** Prominent warning in standard_layer.rs and any CHIP-0057 receive code

## Multi-Input Aggregation Risk

**Context:**
- CHIP-0057 silent payment aggregation requires controlling ALL inputs in a transaction
- File: `crates/chia-sdk-driver/src/action_system/spends.rs` line 465 — `synthetic_keys: &IndexMap<Bytes32, PublicKey>`
- This maps asset (usually puzzle_hash) to its synthetic key

**The hazard:**
```rust
// UNSAFE pattern if some inputs are uncontrolled:
let mut aggregated_sk = aggregate_sender_sks(&my_keys)?;  // Only my keys
// If transaction has inputs from co-signer, aggregation is WRONG
// Silent payment detection will fail or produce detectable pattern
```

**Multi-party scenarios:**
- Offer protocol: One party provides inputs; counterparty approves
- CoinSet mixing: Multiple unrelated inputs in single bundle
- Multi-sig: M-of-N signatories must all participate in aggregation

**Current mitigation (partial):**
- File: `crates/chia-sdk-driver/src/clear_signing.rs` line 519 — TODO comments on vault-of-vault handling
- No explicit "aggregate_sender_sks" function visible in SDK (likely deferred or upstream)

**Mitigations:**
1. **API design:** When CHIP-0057 aggregation is implemented:
   - Require explicit `all_sender_keys: Vec<SecretKey>` parameter
   - Count inputs: `assert_eq!(tx.inputs.len(), all_sender_keys.len())`
   - Fail loudly if mismatch — do NOT fall back to single-input mode
2. **Offers/Bundles:** Aggregation must happen at sign-time across all parties
   - Each party signs with their slice of keys
   - Master aggregation happens only after all parties have signed
3. **Testing:** Unit tests must cover:
   - Single input (aggregation = identity)
   - Multiple inputs (correct aggregation)
   - Mismatch (must panic, not silently downgrade)
