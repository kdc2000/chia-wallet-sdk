# Phase 09.2: Harden SP sender keys — Context

**Gathered:** 2026-06-01
**Status:** Ready for planning
**Source:** Design settled directly with user (2026-06-01), grounded in `ISSUE-silent-payment-synthetic-key-guard.md` + live-code verification.

<domain>
## Phase Boundary

Eliminate the silent-fund-loss footgun in the CHIP-0057 send path where `Spends::with_silent_payment_keys` requires synthetic sender keys but enforces it nowhere. A wallet that registers RAW keys (the natural mistake, since the standard-spend path synthesizes for the caller while the SP path uses keys verbatim) gets a valid-looking signed bundle whose output lands at a one-time puzzle hash no CHIP-0057 scanner can detect or spend — silent, post-broadcast, unrecoverable.

In scope: the runtime guard, the Rust newtype, raw-key binding methods on all three targets, and updating the in-repo callers (example + e2e test) + descriptor + per-language tests.

Out of scope: the receive-side `SilentPaymentKeys` (scan/spend) types; the `ScalarField` signed/unsigned boundary (already handled); any change to the on-chain derivation math (a correct synthetic key must still produce the byte-identical one-time PH — no detection-oracle regression).
</domain>

<decisions>
## Implementation Decisions (LOCKED)

### Layered defense (all three; not redundant)
- GUARD-02 (newtype) = compile-time "did you synthesize?" — Rust only.
- GUARD-01 (runtime guard) = "and does it match THIS coin?" — universal; the only guard across FFI; backstop for the `_unchecked` path. **Keep it even though the newtype exists.**
- GUARD-03 (raw-key bindings) = ergonomic FFI surface; synthesizes internally; protected by GUARD-01.

### GUARD-01 — runtime guard
- Location: `crates/chia-sdk-driver/src/action_system/spends.rs`, in `sp_finish_branch` (where the existing presence/coverage gates and the coin's `p2_puzzle_hash` live). Eager validation at `with_silent_payment_keys` registration is acceptable too — planner's call; finish-time keeps all SP gates co-located and is the latest-but-still-pre-sign point.
- Check, per non-ephemeral XCH input keyed by `ph = item.asset.p2_puzzle_hash()`:
  - `StandardArgs::curry_tree_hash(registered_pk) == ph` (validates against the actual coin → accepts default AND custom-hidden synthetic keys; rejects raw).
  - `registered_sk.public_key() == registered_pk` (sk/pk map consistency).
- On failure: `return Err(DriverError::SilentPaymentKeyNotSynthetic)` BEFORE any signing. New variant added to `crates/chia-sdk-driver/src/driver_error.rs` alongside the other `SilentPayment*` variants.
- Must fire for single-input too (the existing `SilentPaymentNoXchInputs`/multi-party gates don't cover synthetic-ness).

### GUARD-02 — `SyntheticSecretKey` / `SyntheticPublicKey` newtypes (Rust)
- Wrap `chia_bls::SecretKey` / `chia_bls::PublicKey`. Live in the driver SP module (consumed by `Spends::with_silent_payment_keys`).
- Constructors: `from_raw(&raw)` → primary, does `derive_synthetic()` (default hidden), so Rust callers get the same raw-in convenience as the bindings; `from_synthetic_unchecked(k)` → documented escape hatch (covered by GUARD-01); `SyntheticSecretKey::public_key() -> SyntheticPublicKey`; inner accessors as needed.
- `Spends::with_silent_payment_keys` signature changes to `IndexMap<Bytes32, SyntheticPublicKey>` / `IndexMap<Bytes32, SyntheticSecretKey>`. Raw-key mistake becomes a **compile error** in Rust.
- Resolves the long-deferred STATE Q2 ("`SyntheticSecretKey` newtype vs documented `&[SecretKey]` parameter").
- Synthesis must route through the SAME `chia_puzzle_types::DeriveSynthetic` path `puzzle_hash_for_pk` uses (signed reducer, default hidden) so outputs stay byte-identical.
- Blast radius (update to compile): `examples/silent_payment.rs`, `crates/chia-sdk-driver/tests/silent_payments_e2e.rs`, and the binding facade's internal map construction.

### GUARD-03 — raw-key binding methods (napi + pyo3 + wasm, ALL THREE)
- Each target's `with_silent_payment_keys` (in `crates/chia-sdk-bindings/src/action_system.rs`) accepts RAW `PublicKey`/`SecretKey` (the newtype can't cross FFI), calls `derive_synthetic()` internally to build the synthetic maps, then drives the Rust core. GUARD-01 is the safety net.
- Update `bindings/action_system.json` descriptor + any `SilentPaymentRegisteredKey` binding shape to reflect raw inputs.
- Document the default-hidden-puzzle assumption: a custom-hidden input fails LOUD via GUARD-01 (`SilentPaymentKeyNotSynthetic`), never silently. (An advanced "already-synthetic" binding entry point is OPTIONAL / deferrable — not required for this phase.)

### Constraints
- ZERO new workspace deps. No new `#[allow]`. `unsafe_code = "deny"`. Feature is `chip-0057`; build each crate ± `--all-features`.
- No regression to the detection oracle: a correct synthetic key must still produce today's exact one-time puzzle hash (pin against the existing Phase-3 CHIP vectors / Phase-6 e2e).

### Claude's Discretion
- Exact module placement of the newtypes; whether GUARD-01 also runs eagerly at registration in addition to finish; precise binding method naming; whether to also delete/repair the now-inaccurate "prevention mechanism" comment at `protocol.rs:123-126` (recommended — it currently misstates that `finish_with_keys` guards synthetic-ness).
</decisions>

<specifics>
## Specific Ideas

- Reproduction & root cause: `ISSUE-silent-payment-synthetic-key-guard.md` (repo root). Raw vs synthetic one-time PH differ (`45c3736f…` raw vs `cf4a72ce…` synthetic in the reporter's fixture).
- Verified-true call sites (current `main`): `with_silent_payment_keys` at `spends.rs:113`; `sp_finish_branch` gates check presence only; `aggregate_sender_sks` sums `from_bytes_raw(sk.to_bytes())` verbatim; `puzzle_hash_for_pk` synthesizes via default `derive_synthetic()`; misleading comment at `protocol.rs:123-126`.
- `chia_puzzle_types::DeriveSynthetic` exposes both `derive_synthetic()` (default hidden) and `derive_synthetic_hidden(&[u8;32])` (custom) — why GUARD-01 validates against the coin rather than assuming default.
</specifics>
