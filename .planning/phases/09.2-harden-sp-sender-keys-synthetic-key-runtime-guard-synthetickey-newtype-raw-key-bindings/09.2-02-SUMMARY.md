# Phase 09.2 Plan 02: SilentPaymentKeyNotSynthetic + GUARD-01 runtime guard Summary

**The CHIP-0057 send path now rejects a non-synthetic (raw, sk/pk-mismatched, or wrongly-`_unchecked`) registered key with `Err(DriverError::SilentPaymentKeyNotSynthetic)` BEFORE signing — a per-input `curry_tree_hash(registered_pk) == coin p2_puzzle_hash` + `sk.public_key() == pk` check in `sp_finish_branch` that fires for single-input too and leaves the detection oracle byte-identical.**

## Accomplishments
- Added `DriverError::SilentPaymentKeyNotSynthetic` (chip-0057 gated) after `SilentPaymentRequiresXch`, with an error message that names the dual invariant and points callers at synthetic keys / `SyntheticSecretKey::from_raw`.
- Inserted GUARD-01 inside the existing non-ephemeral XCH loop in `sp_finish_branch`, after the SK-coverage lookup and before `sender_sks.push`. Per input it checks `Bytes32::from(StandardArgs::curry_tree_hash(*pk)) != ph || sk.public_key() != *pk` and returns the typed error on mismatch. The PK map is bound once before the loop (`synthetic_pks = spends.silent_payment_synthetic_pks.as_ref()`) to avoid re-borrowing `spends` while `secret_keys` is live.
- The guard validates against the spent coin's actual `p2_puzzle_hash` — so it accepts both default AND custom-hidden synthetic keys and rejects raw keys, and it covers the single-input case (the loop runs for count == 1).
- Updated the `sp_finish_branch` gate-ordering rustdoc to list GUARD-01 between the SK-coverage check and the no-inputs guard.
- Added three negative tests to `send_keys.rs` proving raw-single-input, sk/pk-mismatch, and `from_synthetic_unchecked`-wrong all fail typed before signing; the existing positive `single_input_accepts_relation_none` (correct key wrapped via `from_synthetic_unchecked(alice.pk)`) still passes — the detection oracle is unbroken.

## Decisions Made
- **Finish-time placement.** GUARD-01 lives in `sp_finish_branch` (invoked by `prepare`, the first call inside `finish_with_keys`) rather than eagerly at `with_silent_payment_keys`. CONTEXT permitted either; finish-time keeps all SP gates co-located and is still strictly pre-sign.
- **Borrow strategy.** Bound the PK map once before the loop (`as_ref()` on a distinct field) per the plan's borrow note — no `mem::take`, no clone, no `#[allow]`.
- **Gate sequencing.** Guard runs after the SK-coverage check (so a missing SK stays `MultiPartyUnsupported`) and before `sender_sks.push` (pre-aggregation, pre-sign). A missing PK-map entry maps to `SilentPaymentKeyNotSynthetic` defensively; in practice GATE 2 guarantees both maps were registered together by `with_silent_payment_keys`.

**2. [Rule 1 - Bug] `sk_pk_mismatch` test used an out-of-group-order SecretKey seed**
- **Found during:** Task 2 (test run)
- **Issue:** The plan's `<behavior>` suggested `SecretKey::from_bytes(&[0x77u8;32])` for the mismatched SK. `[0x77; 32]` exceeds the BLS12-381 subgroup order, so `from_bytes` returned `Err("SecretKey byte data must be less than the group order")` and the test failed before reaching the guard.
- **Fix:** Used `SecretKey::from_bytes(&[0x01u8; 32])` (a small value well under the group order, distinct from `alice.sk`) so `from_bytes` succeeds and the registered sk's `public_key() != pk`, exercising GUARD-01's second arm exactly as intended.
- **Files modified:** crates/chia-sdk-driver/src/silent_payments/send_keys.rs
