# Phase 04.2: Unify SP send into Action::send via SendDestination enum — Context

**Gathered:** 2026-05-17
**Status:** Ready for planning

<domain>
## Phase Boundary

Fold the silent-payment send-side API into the generic `Action::send` surface. After this phase:

- A new `SendDestination` enum (with `PuzzleHash(Bytes32)` always-on + `SilentPayment(SilentPaymentAddress)` chip-0057-gated) replaces the bare `puzzle_hash: Bytes32` field on `SendAction`.
- `Action::send(id, destination, amount, memos)` is the single send-action constructor for both regular and SP destinations.
- SP keys are registered on `Spends` via `with_silent_payment_keys(pks, sks)` builder; the dedicated `Spends::finish_with_silent_payment_keys` method goes away (its derivation pipeline absorbs into a chip-0057 branch of `Spends::finish_with_keys`).
- `Action::silent_payment_send` constructor, `Action::SilentPaymentSend` enum variant, and `actions/silent_payment_send.rs` are deleted.
- `crates/chia-sdk-driver/src/silent_payments/send_keys.rs` either disappears or shrinks to a chip-0057-gated derivation helper called by the finish path.
- All Phase 4.1 work (the `Relation::AssertConcurrent` requirement, the input-binding gate, the cycle pinning test, the `Relation` rustdoc) carries forward unchanged in behavior; only the call shape of the gate fires changes.

**Not in scope** (these are separate efforts):
- Phase 5's binding descriptor update (`SendDestination` opaque-handle class entry in `bindings/action_system.json`) — Phase 5 carries it.
- Any Sage-repo changes — Sage is a separate repo; `impl From<Bytes32> for SendDestination` means Sage's 12 existing `Action::send` call sites compile unchanged with zero work on their side.
- CAT2 / NFT silent payments (deferred to v2 per PROJECT.md "Out of Scope").

</domain>

<decisions>
## Implementation Decisions

### Naming
- **D-01:** New enum is named **`SendDestination`**. Mirrors the existing `SingletonDestination` precedent already imported and used in `crates/chia-sdk-driver/src/actions/send.rs:6` (`SingletonDestination::CreateCoin` dispatch for DID/option branches at lines 81 and 87). Self-documenting; conventionally placed.
- **D-02:** Variant naming: `SendDestination::PuzzleHash(Bytes32)` and `SendDestination::SilentPayment(SilentPaymentAddress)`. The chip-0057 variant is `#[cfg(feature = "chip-0057")]`-gated.

### Migration posture
- **D-03:** **Hard break** — delete the old API in this phase, no `#[deprecated]` forwarders, no version bump grace period. Specifically:
  - `Action::SilentPaymentSend(SilentPaymentSend)` enum variant — deleted from `crates/chia-sdk-driver/src/action_system/action.rs`.
  - `Action::silent_payment_send(recipient, amount, memos)` constructor — deleted (currently at lines 238-245 of `action.rs`).
  - Dispatch arms at `action.rs:274` (`calculate_delta`) and `action.rs:297` (`spend`) — deleted.
  - `Spends::finish_with_silent_payment_keys` method (in `crates/chia-sdk-driver/src/silent_payments/send_keys.rs:69-180`) — deleted; its derivation pipeline moves into a chip-0057-gated branch of `Spends::finish_with_keys` in `action_system/spends.rs`.
  - `crates/chia-sdk-driver/src/actions/silent_payment_send.rs` (640 lines) — deleted; tests relocate (planner decides destination per SC11 below).
  - Justification: SDK is pre-1.0 (per PROJECT.md), Phase 5 (Bindings) hasn't started so no shipped binding consumer uses the old factory, Sage's main repo has zero `Action::silent_payment_send` callers, all internal SDK call sites are inside `actions/silent_payment_send.rs::tests` and `silent_payments/send_keys.rs::tests` (both updated as part of this refactor anyway).

### Public API surface for SP derivation primitives
- **D-04:** **Keep `pub` visibility** on the three Phase 4 Plan 04-01 primitives:
  - `derive_one_time_puzzle_hash(scan_pk, spend_pk, agg_sk, input_hash, k) -> Bytes32`
  - `compute_input_hash(coin_ids, agg_sender_pk) -> Bytes32`
  - `aggregate_sender_sks(sks) -> SecretKey`
  - Justification (3 reasons): (1) Phase 4 deliberately made them pub for CHIP-test-vector observability (TV1/TV4 byte-pinned tests in `silent_payments/` are useful to external consumers verifying the SDK matches the spec); (2) Sage's existing model (per `~/silent-payments/send_payment.py` lines 242/302-306/348) is "wallet pre-computes onetime_puzzle_hash itself, emits a regular `CREATE_COIN`" — a supported pattern under Design C alongside the canonical `Action::send` path; (3) smallest delta from current state — `pub(crate)` would force migration of the test surface and remove an intentional Phase 4 capability.

### Spends key-registration ergonomics
- **D-05:** **Mutating + chainable** builder method:
  ```rust
  pub fn with_silent_payment_keys(
      &mut self,
      synthetic_pks: IndexMap<Bytes32, PublicKey>,
      synthetic_sks: IndexMap<Bytes32, SecretKey>,
  ) -> &mut Self
  ```
  - `#[cfg(feature = "chip-0057")]` gated.
  - Mutating matches the `add_*` pattern already in use on `Spends` (`add`, `add_optional_condition`, `add_required_condition`).
  - `&mut Self` return enables chaining but doesn't force it.
  - **NOT** offered as an alternate constructor (no `Spends::new_with_silent_payment_keys`) — Sage-style callers build `Spends`, conditionally configure keys when any destination is SP, then `apply` + `finish`. One entry point.
  - **NOT** offered as a non-chainable setter (no `set_silent_payment_keys`) — chainable is strictly more flexible.

### Public surface preserved from Phase 4.1
- **D-06:** Phase 4.1 work carries forward in behavior, unchanged:
  - `DriverError::SilentPaymentRequiresInputBinding` variant — kept, same wording, fires from the new chip-0057 branch of `Spends::finish_with_keys` instead of from `finish_with_silent_payment_keys`.
  - `Relation::AssertConcurrent` requirement for multi-input SP — kept; the gate moves but the rule doesn't change.
  - Parametric cycle pinning test (`assert_concurrent_relation_emits_cycle_for_n_coins_{2,3,4}` in `action_system/spends.rs::tests`) — untouched.
  - `Relation` enum rustdoc — untouched; remains the load-bearing CHIP-0057 Pass 2b reference.

### Claude's Discretion
The following are left to the planner to decide based on file-size / cohesion / convention concerns at planning time. Roadmap SCs constrain the outcome but not the path:

- **`SendDestination` file location** — `action_system/send_destination.rs` (next to `Action`/`Relation`, concept-grouped) or `actions/send_destination.rs` (next to `SendAction`, consumer-grouped). Either is defensible.
- **Finish entry point** for the SP derivation branch — most likely `Spends::finish_with_keys` (the current generic finish that takes pks), but the planner may surface a better fit during research.
- **Test file destinations** for the 8 tests deleted from `actions/silent_payment_send.rs` + 2 from `silent_payments/send_keys.rs` — could land in `actions/send.rs::tests` (chip-0057 branch), `action_system/spends.rs::tests` (alongside pinning tests), or a new dedicated `silent_payments/tests.rs`. Planner decides based on what keeps each file under reasonable size + maximizes test-near-code cohesion.
- **New error variant exact wording** — within the semantics of SC8/SC9:
  - `SilentPaymentKeysNotRegistered` — fires when `SendDestination::SilentPayment` is applied but `with_silent_payment_keys` was never called before finish.
  - `SilentPaymentRequiresXch` — fires when `SendDestination::SilentPayment(...)` is used with `Id != Id::Xch`.
  - Exact `#[error("...")]` strings are the planner's call within those meanings.
- **Apply-time gate placement** for `SilentPaymentRequiresXch` — fire inside `SendAction::spend` chip-0057 branch (runtime), since `Action::send` is infallible. (Construction-time enforcement would require making `Action::send` fallible, breaking all 28 callers.)
- **Memo-hint guard relocation** — currently in `SilentPaymentSend::apply` (inside the to-be-deleted action). Moves to the chip-0057 SP arm of `SendAction::spend`. Same semantic behavior; planner decides exact factoring.

</decisions>

## Existing Code Insights

### Reusable Assets
- **`SingletonDestination` enum** (used in `actions/send.rs:6` import, lines 81/87 dispatch for DID and option destinations) — direct naming + dispatch precedent for `SendDestination`. The planner should mirror its shape and import location.
- **`Spends::add_*` mutating-method pattern** (`add`, `add_optional_condition`, `add_required_condition` in `action_system/spends.rs`) — pattern precedent for `with_silent_payment_keys` (D-05).
- **`impl From<X> for Y` ergonomic-conversion pattern** (used throughout the codebase for ID types) — the `impl From<Bytes32> for SendDestination` keeps all 28 existing `Action::send(id, ph, ...)` Rust callers compiling unchanged.
- **Phase 4.1's runtime gate + cycle pinning test + Relation rustdoc** — preserved unchanged; D-06 explicitly carries them forward.
- **Opaque-handle bindings precedent (`Id`, `Action` in `bindings/action_system.json`)** — Phase 5's descriptor update for `SendDestination` slots into this pattern with zero bindy macro work.

### Established Patterns
- **chip-0057-gated enum variants** — pattern: `#[cfg(feature = "chip-0057")]` directly on the variant. The `SilentPayment(SilentPaymentAddress)` variant follows this.
- **chip-0057-gated `DriverError` variants** — pattern: `#[cfg(feature = "chip-0057")]` on the variant + a `#[error(...)]` description. Precedents in `driver_error.rs`: `SilentPaymentMultiPartyUnsupported`, `SilentPaymentMemoHintForbidden`, `SilentPaymentRequiresInputBinding`. The two new variants (`SilentPaymentKeysNotRegistered`, `SilentPaymentRequiresXch`) follow this pattern.
- **`SendAction::spend` dispatch-by-`Id` pattern** (`actions/send.rs:42-90` — XCH branch, CAT branch, DID branch, NFT branch, option branch). New chip-0057-gated inner dispatch on `self.destination` slots into the XCH branch (or, if the planner picks differently, wraps the outer dispatch).
- **Privacy-warning rustdoc** (per Phase 4 SEND-08; 7 mentions across SP surfaces verified via `grep -L 'Privacy warning'` gate) — every memo-bearing public surface in `silent_payments/` and `actions/silent_payment_send.rs` carries the warning. After 04.2, the warning must move to wherever the public SP surface now lives (most likely `Action::send` itself or `SendDestination::silent_payment`).

### Integration Points
- **`SendAction::spend`** (`actions/send.rs:34-93`) — receives the new chip-0057-gated dispatch arm. When `self.destination` is `SendDestination::SilentPayment(addr)`, the apply-time SP logic (reserve XCH parent via `output_source`, push to `silent_payments_pending`, increment per-`scan_pk` `k` counter, memo-hint guard) fires here instead of in the deleted `SilentPaymentSend::spend`.
- **`Spends::finish_with_keys`** (`action_system/spends.rs:472`) — receives the chip-0057-gated SP derivation branch. The 04.1 input-binding gate fires here; SK-coverage check, input_hash computation, per-pending derive + push CreateCoin, push to `outputs.xch` all absorb here from the deleted `finish_with_silent_payment_keys`.
- **`Spends` struct fields** — gains 2 new chip-0057-gated `Option<IndexMap<Bytes32, PublicKey>>` and `Option<IndexMap<Bytes32, SecretKey>>` fields (or one bundled struct). Existing `silent_payment_counters` and `silent_payments_pending` fields preserved.
- **`Action::send` constructor** — signature changes from `(id, puzzle_hash: Bytes32, amount, memos)` to `(id, destination: SendDestination, amount, memos)`. All 28 existing Rust callers compile unchanged via `From<Bytes32>`.
- **`bindings/action_system.json`** — Phase 5 (not 04.2) will add the `SendDestination` opaque-handle class entry and remove the `Action.silent_payment_send` factory. SC12 pre-commits the descriptor pattern.

<specifics>
## Specific Ideas

- **Sage's `Wallet::send_xch` is the model.** A wallet's send code should be able to dispatch a regular vs. SP send by parsing the address string and mapping to the right `SendDestination` variant — nothing more. Per Sage `xch.rs:13-52` (the entire current `send_xch` flow). After 04.2 + Phase 5, Sage gaining SP support is one new branch in `send_xch`, not a new method.
- **The Python prototype shows the canonical wallet-side derivation sequence** (`~/silent-payments/send_payment.py:242, 302-306, 348`). D-04 (keep primitives pub) is exactly what makes that sequence portable into the Rust SDK without forking. A wallet author writing custom logic that pre-computes the puzzle hash can do so.
- **Bindy opaque-handle pattern is verified ahead of Phase 5.** During discussion I read `crates/chia-sdk-bindings/bindy-macro/src/lib.rs:37-59` and confirmed the `Binding` schema has exactly three kinds: `Class`, `Enum { values: Vec<String> }` (unit-variants only), `Function`. Tagged unions aren't expressible. Phase 5's `SendDestination` descriptor will look like (~12 JSON lines):
  ```json
  "SendDestination": {
    "type": "class",
    "methods": {
      "puzzle_hash":       { "type": "factory", "args": { "puzzle_hash": "Bytes32" } },
      "silent_payment":    { "type": "factory", "args": { "address": "SilentPaymentAddress" } },
      "is_puzzle_hash":    { "return": "bool" },
      "as_puzzle_hash":    { "return": "Option<Bytes32>" },
      "is_silent_payment": { "return": "bool" },
      "as_silent_payment": { "return": "Option<SilentPaymentAddress>" }
    }
  }
  ```
  No new bindy macro work required. 04.2 doesn't write this — it just ensures the Rust shape supports it.

</specifics>

<deferred>
## Deferred Ideas

- **Sage-side adapter PR** (`Wallet::send_xch` gaining a SP destination branch) — Sage is a separate repo. Out of scope for 04.2. The `From<Bytes32>` impl means Sage's existing XCH-only `send_xch` keeps working; adding SP is a wallet-side concern that lands on Sage's timeline after Phase 5 ships bindings.
- **CAT2 / NFT silent payments** — already deferred to v2 per PROJECT.md "Out of Scope" (CAT2 send works constructively but receivers can't detect them without indexer support; NFT singletons add complexity that doesn't justify v1).
- **Auto-derive SP keys from a registered `SignerContext`** — a future ergonomic might be `Spends::with_signer(&signer)` that pulls SP-relevant SKs automatically. Out of scope; D-05 commits to the explicit `with_silent_payment_keys(pks, sks)` shape.
- **Deprecation forwarders for the old API** — explicitly rejected per D-03. If a v0.x consumer somewhere has typed `Action::silent_payment_send(...)`, their compile breaks and they update to `Action::send(Id::Xch, recipient.into(), ...)`. Pre-1.0 is the time for these breaks.

</deferred>
