## Naming

| Option | Description | Selected |
|--------|-------------|----------|
| `SendDestination` | Matches existing `SingletonDestination` naming precedent in same file. Self-documenting. Already locked in roadmap entry. | ✓ |
| `XchDestination` | Honest about scope but misleading — `PuzzleHash` variant is used for all asset types in current `SendAction` dispatch. | |
| `Recipient` | Cleaner but conflicts with `SilentPaymentAddress` mental model (the address IS the recipient). | |

**User's choice:** `SendDestination` (recommended).
**Notes:** Sticks to roadmap entry's pre-locked naming. `SingletonDestination` precedent at `actions/send.rs:6` is the decisive convention match — same file even uses it for DID/option destination dispatch at lines 81/87.

## Migration posture

| Option | Description | Selected |
|--------|-------------|----------|
| Hard break | Delete `Action::silent_payment_send`, `Action::SilentPaymentSend` variant, `Spends::finish_with_silent_payment_keys`, and `actions/silent_payment_send.rs` immediately. Pre-1.0, no shipped consumer affected, planning artifacts already assume this. | ✓ |
| Deprecation period | Keep both as `#[deprecated]` forwarders that call the new API. ~50 lines of forwarder code + `#[allow(deprecated)]` on internal call sites. Buys grace for hypothetical consumers but conflicts with pre-1.0 posture. | |
| Hybrid: delete action, deprecate finish-method | Delete the action variant cleanly, keep `finish_with_silent_payment_keys` as a thin `#[deprecated]` forwarder that calls `with_silent_payment_keys` + `finish_with_keys`. | |

**User's choice:** Hard break (recommended).
**Notes:** Justified by pre-1.0 status (PROJECT.md), zero Sage call sites for `Action::silent_payment_send`, Phase 5 not yet started, and all internal SDK call sites being inside tests that get updated as part of this refactor anyway.

## Pre-derivation primitives

| Option | Description | Selected |
|--------|-------------|----------|
| Keep public | Phase 4 deliberately made them `pub`. Sage's model + CHIP test-vector observability both favor public. The new `Action::send` canonical path doesn't preclude pre-derivation use. Smallest delta from current state. | ✓ |
| Make `pub(crate)` | Forces the `Action::send` + `with_silent_payment_keys` path. Reduces surface area. Wallet authors who want pre-derivation would have to re-implement or fork. | |
| Public but rustdoc-discouraged | Keep `pub`, add a "prefer Action::send" privacy/correctness warning in rustdoc. | |

**User's choice:** Keep public (recommended).
**Notes:** Sage's Python prototype (`~/silent-payments/send_payment.py:242, 302-306, 348`) does exactly the pre-derivation flow these primitives enable. Keeping them public means the Sage-style flow is a first-class supported pattern, not a hack.

## Spends key-registration ergonomics

| Option | Description | Selected |
|--------|-------------|----------|
| `with_silent_payment_keys` mutating, chainable | `pub fn with_silent_payment_keys(&mut self, pks, sks) -> &mut Self`. Matches the `add_*` mutating-method pattern on Spends; chainable for callers that want it; chip-0057 gated. | ✓ |
| `set_silent_payment_keys`, no chaining | `pub fn set_silent_payment_keys(&mut self, pks, sks)`. Returns nothing. Matches `add` exactly. | |
| Both: builder + alt constructor | Add `Spends::new_with_silent_payment_keys(change_ph, pks, sks)` constructor in addition to the builder. | |

**User's choice:** `with_silent_payment_keys` mutating, chainable (recommended).
**Notes:** One entry point is enough; Sage-style callers build `Spends`, conditionally configure keys if any destination is SP, then `apply` + `finish`. Constructor variant adds surface for marginal ergonomic gain. `&mut Self` return enables chaining without forcing it.
