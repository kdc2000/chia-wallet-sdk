# Phase 04.2: Unify SP send into Action::send via SendDestination enum — Research

**Researched:** 2026-05-17
**Domain:** Rust refactor — folding a chip-0057-gated SP action variant into a unified send-action surface via a new enum
**Confidence:** HIGH (every claim verified against the working tree; all line numbers / call sites grep-verified)

## Summary

The design space for Phase 04.2 is fully locked by CONTEXT.md (D-01 through D-06). This research delivers the **line-level, file-level, ordering-level guidance** the planner needs to break the refactor into atomic-commit tasks without breaking the workspace build between commits.

Key findings:

1. **28 `Action::send` callers verified** (16 SDK + 12 Sage). All survive unchanged via `impl From<Bytes32> for SendDestination` because every existing caller passes a `Bytes32` literal — not a `SendDestination` value. Confirmed by reading `/mnt/work/sage/crates/sage-wallet/src/wallet/{xch,options,dids,multi_send,cats,nfts,coin_management,offer/make_offer}.rs`. The bindings facade `crates/chia-sdk-bindings/src/action_system.rs:294` passes `puzzle_hash: Bytes32` — also survives via `From`.
2. **15 internal `Action::silent_payment_send` call sites + 5 `finish_with_silent_payment_keys` call sites** all live inside the two doomed test blocks (`actions/silent_payment_send.rs::tests` 8 fns; `silent_payments/send_keys.rs::tests` 3 fns). No production callers anywhere.
3. **Three field-mirror sites for the 2 new `Spends` chip-0057 fields**: struct def (lines 28-31), `with_separate_change_puzzle_hash` constructor (lines 78-81), `prepare` migration to `Spends<Finished>` (lines 464-467). Existing `silent_payment_counters` and `silent_payments_pending` are the exact precedent — mirror placement.
4. **`SendAction` loses `Copy`** after the refactor: `SilentPaymentAddress` is `Clone` only (contains `PublicKey` which is Copy in chia-bls 0.36.1, BUT `SilentPaymentNetwork` enum is also clone-only). `SendDestination` is `Clone` only. The current `#[derive(Debug, Clone, Copy)]` on `SendAction` (`actions/send.rs:9`) becomes `#[derive(Debug, Clone)]`. `Action` is already `Clone`-only so no upstream impact.
5. **Atomic-commit ordering is recoverable**: a Wave-A "introduce-additive" pass (new enum + new finish branch + new `Spends` fields + new builder + `impl From<Bytes32>` + new error variants) keeps the workspace green; a single Wave-B "delete-and-migrate" commit deletes the old API + updates all 15 test call sites in one atomic step. The blocker is the apply-time dispatch — `SendAction::spend` needs the chip-0057 SP branch landed BEFORE the file deletion. See §"Atomic Commit Sequencing".
6. **Bindy descriptor pattern verified for Phase 5**: `bindy-macro` schema (`Binding::{Class, Enum{values:Vec<String>}, Function}`, `MethodKind::{Normal, Async, ToString, Static, Factory, AsyncFactory, Constructor}`) supports the `Id`-style opaque-handle (factory methods + accessor methods). `Option<SilentPaymentAddress>` return type is parseable through the same machinery `as_existing -> Option<Bytes32>` and `as_new -> Option<usize>` already use on the `Id` class.

**Primary recommendation:** Plan as two waves — Wave A (additive, build green at every commit) and Wave B (a single delete-and-migrate atomic commit that updates 15 test call sites + deletes 2 files/methods + removes the old enum variant). Locate `SendDestination` at `action_system/send_destination.rs` (concept-grouped with `Action`/`Relation`/`Id`, since the enum is consumed by `SendAction` but conceptually belongs to the action-construction surface alongside `Id`). Place the SP derivation branch at the top of `Spends::finish_with_keys` (lines 472-507) as a pre-emit short-circuit, gated by `#[cfg(feature = "chip-0057")]`, before the standard `prepare → unspent → spend` flow.

### Pattern 1: `SingletonDestination` enum precedent

`SingletonDestination` (`action_system/singleton_spends.rs:537-540`) is the exact precedent. Its definition:

```rust
// Source: action_system/singleton_spends.rs:537
#[derive(Debug, Clone, Copy)]
pub enum SingletonDestination {
    CreateCoin(CreateCoin<NodePtr>),
    Melt,
}
```

It's consumed in `actions/send.rs:81,87` (`SingletonDestination::CreateCoin(create_coin)`) and in `actions/melt_singleton.rs:30,33` (`SingletonDestination::Melt`). Lives in `action_system/` not `actions/`. The `SendDestination` enum follows the same pattern with two differences:

1. `SendDestination` cannot derive `Copy` because `SilentPaymentAddress` is `Clone`-only (`crates/chia-sdk-utils/src/silent_payments/address.rs:53`: `#[derive(Clone, Debug, PartialEq, Eq)]`).
2. The second variant is chip-0057-gated:

```rust
#[derive(Debug, Clone)]
pub enum SendDestination {
    PuzzleHash(Bytes32),
    #[cfg(feature = "chip-0057")]
    SilentPayment(SilentPaymentAddress),
}

impl From<Bytes32> for SendDestination {
    fn from(puzzle_hash: Bytes32) -> Self {
        Self::PuzzleHash(puzzle_hash)
    }
}
```

### Pattern 2: chip-0057-gated `Spends` field

The existing precedent (`action_system/spends.rs:28-31`):

```rust
#[cfg(feature = "chip-0057")]
pub(crate) silent_payment_counters: std::collections::HashMap<[u8; 48], u32>,
#[cfg(feature = "chip-0057")]
pub(crate) silent_payments_pending: Vec<crate::silent_payments::SilentPaymentPending>,
```

The 2 new fields mirror this exactly:

```rust
#[cfg(feature = "chip-0057")]
pub(crate) silent_payment_synthetic_pks: Option<IndexMap<Bytes32, PublicKey>>,
#[cfg(feature = "chip-0057")]
pub(crate) silent_payment_synthetic_sks: Option<IndexMap<Bytes32, SecretKey>>,
```

(Or one bundled struct. Two separate `Option<IndexMap<...>>` fields recommended — see §"Two fields vs one bundle".)

`Option<...>` is critical: `None` means "no keys registered" (triggers `SilentPaymentKeysNotRegistered` at finish), `Some(map)` means "keys registered". This is the structural enforcement that replaces what the dedicated `finish_with_silent_payment_keys` method's signature used to provide.

Precedent (`driver_error.rs:148-158`):

### Pattern 4: Two fields vs one bundle (for the SP keys on `Spends`)

**Recommend two separate `Option<IndexMap<...>>` fields**, not one bundled struct, for three reasons:

1. **Mirrors existing precedent.** `silent_payment_counters` and `silent_payments_pending` are separate fields, not a `SilentPaymentState` bundle. Consistency wins.
2. **`with_silent_payment_keys` is the only setter.** Both fields are set together via the builder (D-05 locks the bundled signature), so the "they should never disagree" argument is enforced at the API surface, not the storage.
3. **Smaller diff.** A bundle struct adds a new type to the crate's public-ish surface (`pub(crate)`); two `Option<IndexMap<_,_>>` are just additions to existing field declarations.

### Anti-Patterns to Avoid

- **DON'T put `SendDestination` in `actions/send_destination.rs`** — even though `SendAction` consumes it, the enum is a *destination type* parameterizing the action, not an action variant. `Id` lives in `action_system/id.rs`, not `actions/id.rs`. `Relation` lives in `action_system/relation.rs`, not `actions/relation.rs`. `SendDestination` belongs in `action_system/`.
- **DON'T make `Action::send` fallible** — would break all 28 callers. Per D-05+Claude-discretion, the `SilentPaymentRequiresXch` gate fires at runtime in `SendAction::spend`, not at construction in `Action::send`.
- **DON'T introduce a `#[deprecated]` forwarder for `Action::silent_payment_send`** — explicitly forbidden by D-03.
- **DON'T expose `Spends::silent_payment_synthetic_pks` / `_sks` publicly** — keep `pub(crate)` like the existing chip-0057 fields. The setter (`with_silent_payment_keys`) is the only public touch point.

## Apply-time dispatch shape

**Current `SendAction::spend` body** (`actions/send.rs:34-93`): an XCH branch (lines 43-61), then `else if` arms for CAT (62-78), DID (79-81), NFT (82-84), option (85-87), with a final `else { Err(InvalidAssetId) }` (88-90).

**After refactor**, the XCH branch (lines 43-61) gets the chip-0057 SP arm. The cleanest factoring (recommendation): keep the outer `if matches!(self.id, Id::Xch)` block and add an inner `match` on `self.destination` ONLY inside that block. The CAT/DID/NFT/option branches never see `SendDestination::SilentPayment` because they have their own destination concept (`SingletonDestination`) and the runtime `SilentPaymentRequiresXch` gate fires inside the chip-0057 SP arm if `Id::Xch` is not the asset.

**The cleanest shape (recommendation, planner picks final factoring):**

```rust
// Source: actions/send.rs (post-refactor sketch)
fn spend(&self, ctx: &mut SpendContext, spends: &mut Spends, _index: usize) -> Result<(), DriverError> {
    // chip-0057 SP path is gated INSIDE the XCH branch (and on Id::Xch).
    // Non-Xch + SP destination is rejected at runtime via SilentPaymentRequiresXch.
    #[cfg(feature = "chip-0057")]
    if let SendDestination::SilentPayment(addr) = &self.destination {
        if !matches!(self.id, Id::Xch) {
            return Err(DriverError::SilentPaymentRequiresXch);
        }
        return spend_silent_payment(ctx, spends, addr, self.amount, self.memos);
        // spend_silent_payment is the relocated body of the deleted
        // SilentPaymentSend::spend (memo_hint_guard inline as line 1).
    }

    // PuzzleHash path — exactly the current dispatch with `self.puzzle_hash` swapped
    // to a `match self.destination` extraction.
    let puzzle_hash = match &self.destination {
        SendDestination::PuzzleHash(ph) => *ph,
        #[cfg(feature = "chip-0057")]
        SendDestination::SilentPayment(_) => unreachable!("handled above"),
    };

    // ... existing XCH / CAT / DID / NFT / option branches with puzzle_hash ...
}
```

**Why this factoring:** the SP branch reuses *none* of the XCH "create CreateCoin + push to outputs.xch" code at apply time (CreateCoin emission is deferred to finish; only `output_source` selection + pending push happen at apply). Pre-empting the XCH branch with the SP arm is structurally simpler than interleaving. The `unreachable!()` in the post-handled match is necessary because Rust's exhaustiveness checker can't see the early return.

## Finish-time branch shape

**Current `Spends::finish_with_keys`** (`action_system/spends.rs:472-507`): drives `prepare()` → `unspent()` → assembles `coin_spends: HashMap<Bytes32, Spend>` → `spends.spend(ctx, coin_spends)`. 36 lines.

**Current `Spends::finish_with_silent_payment_keys`** (`silent_payments/send_keys.rs:74-180`): 9-step body — empty-pending short-circuit (delegates to `finish_with_keys`), input-binding gate (04.1), SK-coverage check, no-inputs guard, aggregate, recover PK, compute input_hash, per-pending derive + push CreateCoin, delegate to `finish_with_keys`. 107 lines.

**After refactor:** the entire SP body absorbs into a chip-0057-gated branch INSIDE `finish_with_keys`, placed BEFORE the `prepare(...)` call so the CreateCoin emissions land in `payment_assertions` and contribute to `prepare`'s `emit_conditions` pass. The new shape:

```rust
// Source: action_system/spends.rs (post-refactor sketch of finish_with_keys)
pub fn finish_with_keys(
    mut self,
    ctx: &mut SpendContext,
    deltas: &Deltas,
    relation: Relation,
    synthetic_keys: &IndexMap<Bytes32, PublicKey>,
) -> Result<Outputs, DriverError> {
    // chip-0057 SP derivation branch — runs BEFORE prepare() so CreateCoin
    // emissions feed into emit_conditions.
    #[cfg(feature = "chip-0057")]
    if !self.silent_payments_pending.is_empty() {
        // (1) D-06 carried-forward input-binding gate.
        let non_ephemeral_xch_count = self.xch.items.iter().filter(|i| !i.ephemeral).count();
        if non_ephemeral_xch_count >= 2 && !matches!(relation, Relation::AssertConcurrent) {
            return Err(DriverError::SilentPaymentRequiresInputBinding);
        }
        // (2) NEW gate per SC8: SP pending exists but keys never registered.
        let Some(sp_sks) = self.silent_payment_synthetic_sks.as_ref() else {
            return Err(DriverError::SilentPaymentKeysNotRegistered);
        };
        // (3) Existing SK-coverage + aggregate + derive + push pipeline
        //     (lines 94-174 of send_keys.rs relocate verbatim, with
        //      `secret_keys` replaced by `sp_sks`).
        // ... (steps 2-8 of the existing finish_with_silent_payment_keys body)
    }

    // PRE-EXISTING finish_with_keys body — prepare/unspent/spend, unchanged.
    let spends = self.prepare(ctx, deltas, relation)?;
    // ...
}
```

**Why this placement (before `prepare`):** the existing `finish_with_silent_payment_keys` works precisely this way (line 84 short-circuits via `self.finish_with_keys(...)`, which itself runs `prepare → unspent → spend`). The CreateCoin emissions from the SP loop populate `self.xch.payment_assertions` and contribute to `prepare`'s `emit_conditions` pass. The borrow-checker workaround at line 139 (`std::mem::take(&mut self.silent_payments_pending)`) carries forward verbatim.

**Where does the synthetic_pks map relate to silent_payment_synthetic_pks?** The existing `finish_with_silent_payment_keys` takes both `synthetic_pks` (for `StandardLayer` signing in the standard `finish_with_keys` delegate) and `secret_keys` (for SP aggregation). After 04.2, the caller passes `synthetic_pks` to `finish_with_keys` (as today) AND has previously registered `silent_payment_synthetic_pks` + `silent_payment_synthetic_sks` via `with_silent_payment_keys`. **These two PK maps can coincide** — callers will typically pass the same map to both, but the SDK keeps them distinct for the rare case where SP signing keys differ from BLS signing keys. The planner may choose to fold them, but the simplest semantics is: `with_silent_payment_keys(pks, sks)` registers BOTH for SP use; `synthetic_keys` (arg to `finish_with_keys`) is used for the standard signer pipeline.

## Common Pitfalls

### Pitfall 1: dead-code-deny on Wave-A additive symbols

**What goes wrong:** Adding `SendDestination`, `with_silent_payment_keys`, the 2 new error variants, the 2 new `Spends` fields in Wave A without any consumer trips `dead_code = "deny"` at the workspace level. CI fails.

**Why it happens:** Workspace lint policy denies dead code; new symbols with no callers register as dead.

**How to avoid:** Pull at least one consumer reshape into Wave A so each new symbol has a live caller before the commit lands. Recommended: include test reshapes in `silent_payments/send_keys.rs::tests` (3 fns) within Wave A so `with_silent_payment_keys` and the new finish-time branch are exercised immediately.

**Warning signs:** `cargo build --workspace --all-features` failing with `dead_code` errors on the new symbols after Wave A.

### Pitfall 2: `Action::send` signature breaks Sage if planner picks `SendDestination` arg instead of `impl Into<SendDestination>`

**What goes wrong:** If `pub fn send(id: Id, destination: SendDestination, amount: u64, memos: Memos)` (literal type) is chosen instead of `impl Into<SendDestination>`, every Sage caller fails to compile — they pass `Bytes32` and Rust does not auto-call `.into()` on a literal parameter.

**Why it happens:** Rust requires `Into` in the signature for implicit `.into()` coercion. Locking the literal type defeats the `From<Bytes32>` impl's whole point.

**How to avoid:** Use `pub fn send(id: Id, destination: impl Into<SendDestination>, amount: u64, memos: Memos)`. Verified by inspection of all 12 Sage call sites — all pass `Bytes32` literals.

**Warning signs:** Sage CI breaks on its next SDK bump; or the local SDK's test call sites in `clear_signing.rs`, `offers/offer.rs`, etc. break.

### Pitfall 3: `SilentPaymentPending` is `pub(crate)` — don't accidentally make it `pub`

**What goes wrong:** When moving the struct's consumer code (the finish-time SP branch) from `silent_payments/send_keys.rs` to `action_system/spends.rs`, the planner might be tempted to upgrade visibility. Don't.

**Why it happens:** Convenience. The struct is consumed via `crate::silent_payments::SilentPaymentPending` field type on `Spends`.

**How to avoid:** Keep `pub(crate) struct SilentPaymentPending` (line 30 of `send_keys.rs`). The new chip-0057 branch in `action_system/spends.rs` already has `crate::` visibility — it can access `pub(crate)` items from sibling modules.

**Warning signs:** Public API surface grows with internal types; bindings work in Phase 5 might accidentally expose `SilentPaymentPending`.

### Pitfall 4: `SendAction` losing `Copy` ripples

**What goes wrong:** `SendAction` currently derives `Copy` (line 9 of `actions/send.rs`). Post-refactor, it cannot — `SilentPaymentAddress` is `Clone`-only. Internal code that depends on `SendAction: Copy` (e.g., `Action::Send(*self)` or array initializations) breaks.

**Why it happens:** Embedded value of a non-Copy type breaks the Copy derive.

**How to avoid:** Grep `SendAction` for any `Copy` reliance before Wave A. Verified via grep — no `Copy`-reliant code in the SDK calls `SendAction` directly; `Action` itself is already `Clone`-only.

**Warning signs:** `cargo build` complains about `Copy` violations on `SendAction` after the derive change in A5.

### Pitfall 5: `Memos::None` literal vs `Memos<NodePtr>::None` explicit form

**What goes wrong:** The existing `SilentPaymentSend::memos` field is typed `Memos<NodePtr>` (explicit), while `SendAction::memos` is typed `Memos` (default type param). Both are the same type at the type-checker level (`Memos<T = NodePtr>` default in `chia-puzzle-types-0.36.1/src/memos.rs:10`). When merging, use the shorter `Memos` form (matches `SendAction`'s precedent + every other action).

**Why it happens:** Plan 04-02 chose the explicit `Memos<NodePtr>` form; the unified `SendAction` should use the implicit form for consistency.

**How to avoid:** Use `memos: Memos` (default `<NodePtr>`) in the new `SendAction` field and `Action::send` signature. Verified by grep: `SendAction::new(id: Id, puzzle_hash: Bytes32, amount: u64, memos: Memos)` (line 18 of `send.rs`) is the precedent.

**Warning signs:** Type inference errors at call sites; redundant turbofish syntax.

### Pitfall 6: Bindings `action_system.json` `send` factory not updated in 04.2

**What goes wrong:** The bindings JSON descriptor's `"send"` factory entry (`bindings/action_system.json:113-117`) currently lists `"puzzle_hash": "Bytes32"`. After 04.2, the Rust signature is `impl Into<SendDestination>`. If 04.2 updates the JSON, Phase 5's BIND-01 plan is half-done; if 04.2 doesn't, the JSON is technically stale until Phase 5.

**Why it happens:** Phase 5 owns bindings JSON updates. 04.2 only changes Rust.

**How to avoid:** Do NOT touch `bindings/action_system.json` in 04.2. The Rust `impl Into<SendDestination>` signature still accepts `Bytes32` from the bindings facade (`crates/chia-sdk-bindings/src/action_system.rs:294` passes `Bytes32`), so the binding facade keeps compiling. The JSON descriptor `puzzle_hash: Bytes32` continues to generate a valid facade call. Phase 5 updates both at the same time.

**Warning signs:** A planner adds `bindings/` edits to a 04.2 task — pushback.

### Pitfall 7: Ordering of new gate vs existing 04.1 gate inside `finish_with_keys` SP branch

**What goes wrong:** The 04.1 `SilentPaymentRequiresInputBinding` gate fires when `non_ephemeral_xch_count >= 2 && relation != AssertConcurrent`. The new `SilentPaymentKeysNotRegistered` gate fires when `silent_payments_pending.len() > 0 && silent_payment_synthetic_sks.is_none()`. If ordered wrong, a multi-input SP send with no registered keys could fail with the wrong error.

**Why it happens:** Both gates fire on the same code path; order matters.

**How to avoid:** Order: `SilentPaymentRequiresInputBinding` FIRST (binding requirement is more fundamental), then `SilentPaymentKeysNotRegistered`. This matches the existing 04.1 placement (between empty-pending short-circuit and SK-coverage check) — the new gate goes immediately after the 04.1 gate. The recommended sketch in §"Finish-time branch shape" reflects this ordering.

**Warning signs:** Test `multi_input_requires_assert_concurrent_relation` (now relocated) starts asserting the wrong error variant.

### Pitfall 8: `Spends` struct field count + drift in `prepare`'s migration

**What goes wrong:** `Spends::prepare` (lines 444-470) manually copies every field across the Unfinished→Finished transition. Adding 2 new fields and forgetting to add them to `prepare`'s `Spends { ... }` constructor at line 454 silently drops the new keys, surfacing as `SilentPaymentKeysNotRegistered` after a confusing detour through `prepare`.

**Why it happens:** Hand-rolled state migration with no derive macro.

**How to avoid:** Edit all THREE sites in lockstep: struct def (28-31), `with_separate_change_puzzle_hash` (78-81), `prepare` migration (464-467). The recommended task A3 lists this triple explicitly.

**Warning signs:** Tests pass `with_silent_payment_keys` but then fail with `SilentPaymentKeysNotRegistered` at finish — keys lost in `prepare`.

## Code Examples

### `SendDestination` enum + `From<Bytes32>` (new file `action_system/send_destination.rs`)

```rust
// Source: derived from CONTEXT.md D-01/D-02 + SingletonDestination precedent
// (action_system/singleton_spends.rs:537-540)
use chia_protocol::Bytes32;

#[cfg(feature = "chip-0057")]
use chia_sdk_utils::silent_payments::SilentPaymentAddress;

/// Where a [`SendAction`] addresses its output: either a literal puzzle hash
/// (the standard case) or a silent-payment address (chip-0057; the recipient
/// publishes one static address and every payment lands at a fresh,
/// unlinkable one-time puzzle hash derived via ECDH).
///
/// `impl From<Bytes32>` lets every existing `Action::send(id, ph, amount, memos)`
/// caller continue to compile unchanged after `Action::send`'s second parameter
/// becomes `impl Into<SendDestination>`.
#[derive(Debug, Clone)]
pub enum SendDestination {
    PuzzleHash(Bytes32),
    #[cfg(feature = "chip-0057")]
    SilentPayment(SilentPaymentAddress),
}

impl From<Bytes32> for SendDestination {
    fn from(puzzle_hash: Bytes32) -> Self {
        Self::PuzzleHash(puzzle_hash)
    }
}
```
