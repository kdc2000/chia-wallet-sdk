<objective>
Revert the bindings `Action.send` to take a raw puzzle hash, add an additive `Action.silentPaymentSend(recipient, amount, memos)` facade + descriptor, and delete the `SendDestination` opaque-handle class from all three binding targets. Migrate the binding tests — including the 7 NON-SP `SendDestination.puzzleHash(...)` sites in `napi/__test__/action_system.spec.ts` (the TS mirror of the Sage E0283/E0560 break).

Purpose: Phase 5 reshaped the binding `Action.send` to require a `SendDestination` opaque handle, which source-broke every non-SP TS `Action.send` caller (Phase 5 Plan 05-04 wrapped 7 sites in `SendDestination.puzzleHash(...)` to work around it — the binding-level analog of the Sage break). This plan makes the binding `Action.send` take a `Bytes32` again and exposes SP send as a separate `Action.silentPaymentSend`, with no break to JS/Python/wasm `Action.send`.

Output: `Action.send(id, puzzleHash, amount, memos)` works with a raw puzzle hash across napi/pyo3/wasm; `Action.silentPaymentSend` is the only SP-send binding surface; `SendDestination` is gone; all four binding targets build and the SP E2E specs pass.

DO NOT touch GUARD-03: `with_silent_payment_keys` (action_system.rs:93-126, taking `Vec<SilentPaymentRegisteredKey>`/`Vec<SilentPaymentRegisteredSecretKey>`) and `Spends.prepare(deltas, Option<Relation>)` (BRIDGE-04) stay exactly as they are. They are in the SAME file as the `Action.send`/`SendDestination` edits — file proximity only, no logical coupling.

DO NOT hand-edit generated artifacts: `napi/index.d.ts`, `napi/index.js`, wasm `.d.ts`, pyo3 `.pyi` regenerate from the facade + descriptor via `napi build` / `wasm-pack build` / `maturin develop`. Rebuilding drops the stale `SendDestination` class automatically.
</objective>
