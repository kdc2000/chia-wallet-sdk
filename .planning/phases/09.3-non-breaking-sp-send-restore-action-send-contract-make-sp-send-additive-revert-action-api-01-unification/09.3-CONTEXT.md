# Phase 9.3 Context — Non-breaking SP send surface (Option A)

## Why this phase exists

Phase 4.2 ("unify SP send into `Action::send` via `SendDestination`", requirement
ACTION-API-01) reshaped a **non-gated, central** public API to fold silent-payment
sends into the generic send constructor. That reshape **source-breaks existing SDK
consumers**, contradicting ACTION-API-01's own claim that "all 28 `Action::send`
callers compile unchanged."

### Empirical evidence (2026-06-03)

Trial-compiled **Sage** (`xch-dev/sage` `main`, pins `chia-wallet-sdk = "0.33.0"`,
features `rustls`/`offer-compression`/`peer-simulator`, **no `chip-0057`**) against
this branch via `[patch.crates-io] chia-wallet-sdk = { path = "/home/kdc/chia-wallet-sdk" }`
then `cargo check -p sage-wallet -p sage -p sage-rpc -p sage-api`:

| Break | Site | Cause |
|-------|------|-------|
| `E0283` ×4 | `sage-wallet/src/wallet/offer/make_offer.rs:92,101,110,119` | `SETTLEMENT_PAYMENT_HASH.into()` — the `impl Into<SendDestination>` param makes the `.into()` target ambiguous (`[u8;32]→Bytes32→SendDestination`). |
| `E0560` ×1 | `sage/src/endpoints/action_system.rs:64` | `SendAction { puzzle_hash }` struct literal — field renamed `puzzle_hash`→`destination` (now `SendDestination`), and `SendAction` lost its `Copy` derive. |

Of Sage's 12 `Action::send` sites, **8 compile fine** (they pass a `Bytes32`
value directly → rescued by `From<Bytes32> for SendDestination`); **4 break**
(they pass `x.into()`). The `From` impl does **not** rescue `.into()` call sites.

With explicit fixes applied (`Bytes32::from(...)`, `destination: puzzle_hash.into()`)
all four Sage crates compiled clean — confirming the breaks are real and the only
SP-caused ones.

### Confound (NOT this phase's concern)

A separate Sage break — `E0063` missing `FeeAction.reserved` at
`sage/endpoints/action_system.rs:138` — comes from **upstream** commit `b3158279`
"Clear signing updates (#349)", not the SP milestone. This reveals the fork is
built on **unreleased upstream** (still labeled `0.33.0`) with SP work commingled
with already-merged upstream changes. That is a distinct PR-prep problem (isolate
SP commits + rebase onto current `Chia-Network/chia-wallet-sdk main`), out of scope
here. When judging the zero-edit acceptance criterion, neutralize this one break.

## Design decision: Option A (chosen with user)

SP send needs more than a `Bytes32` (recipient address + finish-time ECDH), so it
can never ride the existing `Bytes32`-typed `send`. Sharing the surface bought
nothing additive couldn't. So: **make SP send a separate, `chip-0057`-gated action;
leave the existing send contract byte-for-byte unchanged.** This is essentially the
shape the milestone shipped at end of Phase 4, before 4.2 unified it.

Rejected alternatives: Option B (keep unified ergonomics as an additive `send_to`),
Option C (deprecate-migrate). A is smallest, fully additive-behind-flag, near-zero
blast radius, easiest upstream review.

## Scope (~22 files, 4 languages)

**Restore the contract:**
- `Action::send(id, puzzle_hash: Bytes32, amount, memos)` — concrete, no `impl Into` (`action_system/action.rs`).
- `SendAction { id, puzzle_hash: Bytes32, amount, memos }` + restore `#[derive(... Copy)]` (`actions/send.rs`). Drop the `SendDestination` match arm from `SendAction::spend`.

**Add SP as a separate gated action:**
- `Action::SilentPaymentSend(SilentPaymentSendAction)` variant (`#[cfg(feature="chip-0057")]`) + `Action::silent_payment_send(recipient, amount, memos)` constructor.
- Relocate the SP send logic (currently the `SendDestination::SilentPayment` arm / `handle_silent_payment_send`) into the action's `SpendAction` impl. `actions/silent_payment_send.rs` already exists as the Phase-4.0 carrier — reuse it.
- Add the two internal gated match arms in `action.rs` (`calculate_delta` + `spend`). `Action` is matched only internally (action.rs:263–294), so this is consumer-invisible.

**Remove `SendDestination` from the public surface:**
- Delete `action_system/send_destination.rs` (or demote `pub(crate)`); drop from `src/prelude.rs`, `silent_payments/types.rs`, `send_keys.rs`, `spends.rs` as needed.

**Bindings (additive, no break to JS/Python `Action.send`):**
- Revert `Action.send` binding to take a puzzle hash; expose `Action.silentPaymentSend(...)` (`chia-sdk-bindings/src/action_system.rs`, `lib.rs`, `bindings/action_system.json`). Remove the `SendDestination` opaque-handle class.
- `Spends.prepare(deltas, Option<Relation>)` stays — already backward-compatible.

**Tests / example / docs:**
- Migrate 10 binding test files (napi/pyo3/wasm) + `examples/silent_payment.rs` + `tests/silent_payments_e2e.rs` from `Action.send(Id, SendDestination.silentPayment(addr), …)` to `Action.silentPaymentSend(addr, …)`.
- `REQUIREMENTS.md`: reframe **ACTION-API-01** (SP is a distinct flag-gated action, not a destination folded into `send`) and **SEND-04** wording.

## Acceptance criteria

1. Existing `Action::send(id, bytes32, …)` AND `Action::send(id, x.into(), …)` call sites compile unchanged (no `E0283`).
2. `SendAction.puzzle_hash` field + `Copy` restored (no `E0560` for struct-literal users).
3. **Sage `main` compiles against this branch with ZERO source edits** — re-run the clone + `[patch]` + `cargo check -p sage-wallet -p sage -p sage-rpc -p sage-api`. (Neutralize the upstream `FeeAction.reserved` confound when judging.)
4. SP send + scan E2E green in Rust + napi + pyo3 + wasm.
5. `cargo fmt`/`clippy`/`machete` clean across all `chip-0057` permutations (on and off, per-crate).

## Open design questions for plan-phase

- Delete `SendDestination` entirely vs keep it `pub(crate)` as an internal helper? (Lean: delete — nothing else needs it once `send` is concrete again.)
- Does `Spends::with_silent_payment_keys` / the finish path need any reshape, or does it already work unchanged with a separate SP action? (The GUARD-01/02/03 work from 9.2 must be preserved exactly — no detection-oracle regression.)
