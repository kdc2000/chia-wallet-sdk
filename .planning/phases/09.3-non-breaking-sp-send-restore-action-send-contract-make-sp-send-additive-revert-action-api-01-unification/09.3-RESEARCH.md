## Summary

This is a **forward hand-edit that reconstructs the pre-Phase-4.2 public contract while preserving every Phase-5-through-9.2 internal**, NOT a `git revert`. A `git revert` of the four 4.2 commits (`5bbb54bc`, `53963ab2`, `19c965d9`, `08411089`, `b1f26930`, `11bf647d`, `4cd99543`, `83013152`) is **infeasible** — Phases 5, 7, 8, 9, 9.1, 9.2 all edited the same files (`actions/send.rs` restructured by 07-02 + 08-03; `send_keys.rs` *replaced* by GUARD-02 newtypes in 09.2-01; `spends.rs` gained GUARD-01 in 09.2-02 + the `Relation` param + `with_silent_payment_keys`; bindings built the entire opaque-handle surface on top). A revert would conflict on every hunk and would *delete* the GUARD/BRIDGE work this milestone depends on.

The good news: the change is genuinely small and mechanical. The pre-4.2 shapes are fully recoverable from git (`git show 5bbb54bc^:<file>`), the apply-time SP logic already lives in a near-self-contained file (`actions/silent_payment_send.rs`, only consumer is one match arm in `SendAction::spend`), and the detection-oracle math (`sp_finish_branch` → `derive_one_time_puzzle_hash`) is **completely decoupled** from `SendDestination` — it reads `silent_payments_pending` + the registered synthetic-key maps off `Spends`, all keyed by puzzle hash. The GUARD-01/02/03 work is therefore orthogonal and survives untouched.

**Primary recommendation:** Reconstruct the pre-4.2 `SendAction`/`Action::send` contract by hand-editing (using `git show 5bbb54bc^:…` as the byte-exact template); convert `actions/silent_payment_send.rs` from a `handle_silent_payment_send` free function into a `SilentPaymentSendAction` struct with a `SpendAction` impl whose `spend()` body is the *current* `handle_silent_payment_send` body verbatim; add the two cfg-gated `Action` enum dispatch arms; delete `SendDestination` entirely; revert the binding `Action.send`/`SendAction` + add `Action.silentPaymentSend`; migrate the 11 test files + example + e2e. Sequence Rust-core-first, then bindings, then tests, gated on the Sage zero-edit recompile + 4-language SP E2E.

## 6. Detection-Oracle Invariant — what pins it, what could perturb it

The one-time puzzle hash for a given `(scan_pk, spend_pk, aggregated_sender_sk, input_hash, k)` is computed by `derive_one_time_puzzle_hash` (called from `sp_finish_branch` at spends.rs:700). **None of its inputs flow through `SendDestination`** — they come from `SilentPaymentPending` (`scan_pk`, `spend_pk`, `k`, `amount`, parent indices) + the aggregated registered SKs. Since the relocation copies the apply-time body verbatim (same `SilentPaymentPending` fields, same k-counter keyed by 48-byte `scan_pk`), the derivation inputs are byte-identical → the output PH is byte-identical.

**Tests that pin the invariant (must stay green, exercise the oracle):**
- `crates/chia-sdk-driver/tests/silent_payments_e2e.rs` — `test_simulator_e2e_unlabeled`, `test_simulator_e2e_labeled`, `test_simulator_e2e_m0_self_change` (3 e2e; each does `Action::send(Id::Xch, SendDestination::SilentPayment(Box::new(addr)), …)` at lines 74, 185, 277, 372 → migrate to `Action::silent_payment_send(addr, …)`).
- `actions/silent_payment_send.rs::silent_payment_tests` — `round_trip_matches_derive_one_time_puzzle_hash` (line 220), `input_hash_round_trip` (line 419) byte-pin against the free-function path; plus the k-counter + memo-guard + Id-guard + keys-not-registered tests (10 total). These move with the relocated file but their `Action::send(…, SendDestination::SilentPayment(…), …)` calls become `Action::silent_payment_send(…)`.
- `send_keys.rs` GUARD tests (lines 167–509) — also use the `SendDestination::SilentPayment` construction shape; migrate to the new constructor.
- Scanner TV tests (`silent_payments/protocol.rs`, `scanner.rs`) pin `derive_one_time_puzzle_hash`/scan against CHIP vectors — they do NOT use the action layer, so they are unaffected by this phase (no migration needed); they are the floor that guarantees the math itself didn't move.

**What could perturb it (watch in plan):** (a) accidentally changing the k-counter key (must stay 48-byte compressed `scan_pk`); (b) accidentally changing guard ordering so `memo_hint_guard` fires after `spend_silent_payment` (currently before — silent_payment_send.rs:32–33); (c) changing `Memos<NodePtr>` vs `Memos` such that the on-chain memo bytes differ. Copy the body verbatim and these cannot regress.

## Common Pitfalls

### Pitfall 1: Attempting `git revert` of the 4.2 commits
**What goes wrong:** Conflicts on every touched file; silently deletes GUARD-01/02/03 and BRIDGE work.
**Why:** Phases 5–9.2 rewrote `send_keys.rs`, restructured `actions/send.rs` (07-02, 08-03), added GUARD-01 to `spends.rs`, and built the entire binding surface on `SendDestination`.
**Avoid:** Forward hand-edit using `git show 5bbb54bc^:<file>` as a byte-exact *template* for the contract shapes only — never `git revert`/`git checkout` whole files.

### Pitfall 2: chip-0057-OFF build break on the new dispatch arm
**What goes wrong:** Forgetting `#[cfg(feature = "chip-0057")]` on either the enum variant OR one of the two dispatch arms → non-exhaustive match (chip-on) or unknown-variant (chip-off).
**Avoid:** Gate all three sites identically; this is the proven pre-4.2 pattern. CI builds each crate with AND without `--all-features`.

### Pitfall 3: `missing_copy_implementations` flips when SendDestination is deleted
**What goes wrong:** The `#[cfg_attr(not(feature = "chip-0057"), allow(missing_copy_implementations))]` on `SendDestination` (send_destination.rs:32) was a 9.1-01 fix for exactly this enum. Once `SendAction` regains `Copy` and `SendDestination` is deleted, that allow goes away — verify no new copy-lint surfaces on the restored `SendAction` (it had `Copy` pre-4.2, so it's fine).
**Avoid:** Run `cargo clippy -p chia-sdk-driver -D warnings` with chip-0057 OFF (the permutation that historically catches these).

### Pitfall 4: Forgetting the non-SP `action_system.spec.ts` revert
**What goes wrong:** Leaving the 7 `SendDestination.puzzleHash(...)` wraps in `napi/__test__/action_system.spec.ts` → references a deleted class → TS compile error.
**Avoid:** These are the TS analog of the Sage break; revert them to plain `Action.send(id, puzzleHash, …)`. Listed in §7.

### Pitfall 5: Memo type drift (`Memos` vs `Memos<NodePtr>`)
**What goes wrong:** Pre-4.2 `silent_payment_send.rs` used `Memos<NodePtr>`; current `action.rs`/`send.rs` use bare `Memos`. Mixing changes on-chain memo bytes / breaks the memo-hint guard test.
**Avoid:** Use bare `Memos` consistently (the 07-02 convention); copy the current `handle_silent_payment_send` body, not the pre-4.2 file.

    }
    fn spend(&self, ctx: &mut SpendContext, spends: &mut Spends, _index: usize) -> Result<(), DriverError> {

## State of the Art

| Old (Phase 4.2 → 9.2 current) | New (Phase 9.3) | Why |
|-------------------------------|-----------------|-----|
| `Action::send(id, impl Into<SendDestination>, …)` | `Action::send(id, Bytes32, …)` concrete | `impl Into` makes `.into()` call sites ambiguous (E0283) — source-breaks consumers |
| `SendAction { destination: SendDestination }`, no `Copy` | `SendAction { puzzle_hash: Bytes32 }` + `Copy` | struct-literal users break (E0560) without the field name/Copy |
| SP send = `SendDestination::SilentPayment` destination | SP send = `Action::SilentPaymentSend` gated variant | additive-behind-flag, zero blast radius on the non-gated `send` |

**Deprecated/removed by this phase:** `SendDestination` enum (driver + binding facade class), the `impl Into<SendDestination>` on `Action::send`.

## Open Questions

1. **Delete `SendDestination` entirely vs `pub(crate)`?**
   - Known: nothing outside the send path needs it once `Action::send` is concrete; the binding class is being removed regardless.
   - Recommendation: **delete entirely.** Keeping it `pub(crate)` adds a dead type (would trip `dead_code = "deny"` unless used). The relocated action carries `SilentPaymentAddress` directly.

2. **Keep `DriverError::SilentPaymentRequiresXch` reachable?**
   - Known: the dedicated `SilentPaymentSendAction` is structurally XCH-only (no `Id` param), so the runtime `SilentPaymentRequiresXch` guard becomes unreachable from the public API.
   - Unclear: whether to (a) drop the variant (it's `chip-0057`-gated; `dead_code`/clippy may flag an unused variant) or (b) keep it for a future CAT-SP path.
   - Recommendation: drop the now-unreachable `SilentPaymentRequiresXch` variant + its test (`silent_payment_destination_requires_xch_id`) to keep `dead_code = "deny"` happy, OR keep the variant and add `#[allow]` with rationale. Lean: **drop it** (smallest surface; v2 CAT-SP can re-add). Plan should make this call explicitly.

3. **`SilentPaymentPending` rustdoc + `spends.rs` comments** still reference `SendDestination::SilentPayment` (types.rs:75, spends.rs:507,544). Pure doc edits — confirm CLEANUP-01 grep gates (`Plan 0[1-6]-` etc.) don't catch the new wording.
