# Phase 04.1 Plan 01: Drop opcode 60/61 announcement emission + update multi-input tests to Relation::AssertConcurrent Summary

Removed the SP-specific empty-message announcement-binding helper + Step 8.5 call site from `Spends::finish_with_silent_payment_keys`; updated the two multi-input tests that previously passed `Relation::None` to use `Relation::AssertConcurrent` (the production-correct value). Multi-input SP transactions now bind via the SDK's existing opcode-64 cycle alone — no SP-uniquely-identifiable on-chain fingerprint remains.

## What Was Built

**Task 1 — `send_keys.rs` (commit `7bf749d1`):** Deleted the 73-line `emit_silent_payment_announcements` method (rustdoc + body, lines 45-116 of the pre-edit file). Deleted the 6-line Step 8.5 call site inside `finish_with_silent_payment_keys`. Cleaned four unused imports (`Bytes`, `Conditions`, `announcement_id`, `SpendKind`). Updated the module-level docstring's final clause from "and (Plan 04-04) emits the opcode 60/61 announcement binding for >=2-input scenarios" to "and relies on the SDK's `Relation::AssertConcurrent` cycle binding (Phase 04.1) for multi-input atomicity". Updated the `multi_party_hard_errors` test to pass `Relation::AssertConcurrent` instead of `Relation::None`; the SK-coverage check still fires first in Step 3, so the expected `Err(DriverError::SilentPaymentMultiPartyUnsupported)` is unchanged.

**Task 2 — `silent_payment_send.rs` (commit `a764436c`):** Deleted the two announcement-specific tests (`single_input_no_announcement` at pre-edit lines 439-498 and `cross_index_announcement_binding` at 500-577) — both verified emission behaviour of the now-deleted helper. Updated the surviving `input_hash_round_trip` test's `finish_with_silent_payment_keys` call to pass `Relation::AssertConcurrent` instead of `Relation::None` (production-correct usage for a 2-input batch; math closure assertion preserved end-to-end).

Net file delta: send_keys.rs 319 → 236 (−83 lines); silent_payment_send.rs 778 → 640 (−138 lines). Total ~221 lines removed.

## Deviations from Plan

### Rule 3 — Blocking issue (task ordering)

**1. Task 1 commit produces transient test-build break until Task 2 lands**

- **Found during:** Task 1 verify step
- **Issue:** Task 1's verify command runs `cargo test --release -p chia-sdk-driver --features chip-0057 silent_payments::send_keys::tests::multi_party_hard_errors -- --exact`, which requires the full lib-test build to succeed. The two tests that Task 2 deletes (`single_input_no_announcement`, `cross_index_announcement_binding`) still reference `spends.emit_silent_payment_announcements(...)` — a method Task 1 just deleted. So the lib-test build fails between Task 1 and Task 2 commits even though the non-test library build is clean.
- **Fix:** Committed Task 1 with the non-test build verified clean and the grep gates green, documented the transient sequencing in the commit message. Task 2 immediately followed, restoring the test build. The final cross-task verification (gates 5-6) confirms all 9 tests pass after both commits.
- **Files modified:** No additional files; sequencing-only.
- **Commits:** Task 1 = `7bf749d1`, Task 2 = `a764436c`.

This is genuinely a plan-structural issue (the plan said "Apply in order" for both tasks), not a code issue. An alternative would have been to reorder execution (Task 2 first, since deleting the call sites first allows Task 1's helper deletion to land with a clean test build). Either ordering produces the same final state. Documenting for future plan authors: when deleting a `pub(crate)` symbol referenced from a `cfg(test)` block in another file, those test deletions should commit either first or atomically with the symbol deletion.
