## 4. Runtime gate location and shape

### 4a. Where to insert

ROADMAP §04.1 SC3 specifies the gate fires when:
- `relation != Relation::AssertConcurrent` AND
- `silent_payments_pending.len() > 0` AND
- ≥2 non-ephemeral XCH inputs

**Insertion point:** Inside `finish_with_silent_payment_keys`, AFTER Step 1's empty-pending short-circuit (line 158-161) and BEFORE Step 2's XCH-input collection (line 163+):

```rust
// Step 1: empty-pending short-circuit (unchanged)
if self.silent_payments_pending.is_empty() {
    return self.finish_with_keys(ctx, deltas, relation, synthetic_pks);
}

// Phase 04.1 input-binding gate: SP multi-input requires Relation::AssertConcurrent
// for Pass 2b scanner detection. Single-input SP sends accept any Relation.
let non_ephemeral_xch_count = self.xch.items.iter().filter(|i| !i.ephemeral).count();
if non_ephemeral_xch_count >= 2 && !matches!(relation, Relation::AssertConcurrent) {
    return Err(DriverError::SilentPaymentRequiresInputBinding);
}

// Step 2 + 3: collect XCH input coin ids + verify SK coverage. (unchanged)
let mut xch_input_ids: Vec<Bytes32> = Vec::with_capacity(self.xch.items.len());
...
```

### 4b. Why this ordering

- Placing the gate AFTER Step 1's short-circuit means non-SP transactions (empty pending) escape without paying the count check, even if relation is None. Correct behavior — only SP transactions care.
- Placing the gate BEFORE Step 2's input-id collection means we don't waste work building the input list if we're about to error out.
- Using `count()` instead of reusing Step 2/3's loop result is intentional: the gate is conceptually separate and reads cleanly; the count is O(n) where n is small.

### 4c. Single-input behavior

Single XCH input + any Relation → gate doesn't fire (count < 2). Phase 4 already supports single-input SP via Pass 1 detection without any binding. Verified by `round_trip_matches_derive_one_time_puzzle_hash` test (single-input case).

## 6. `Relation` enum rustdoc + pinning test

### 6a. Current rustdoc state

`crates/chia-sdk-driver/src/action_system/relation.rs` (full file, 6 lines):
```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub enum Relation {
    None,
    AssertConcurrent,
}
```

**No rustdoc on the enum or any variant.** Phase 4.1 SC5 requires adding documentation that names CHIP-0057 Pass 2b as the consumer.

### 6b. Proposed rustdoc

```rust
/// How a multi-coin `Spends` bundle binds its inputs together so that no
/// single coin spend can be replayed independently of its sibling spends.
///
/// The binding mechanism is also load-bearing for CHIP-0057 silent-payment
/// scanner detection (Pass 2b): scanners reconstruct multi-input SP spend
/// groups by computing strongly connected components over the directed
/// graph of `ASSERT_CONCURRENT_SPEND` (opcode 64) references in each
/// removal's solution. See `silent_payments/send_keys.rs::finish_with_silent_payment_keys`
/// for the SP-side enforcement and the CHIP-0057 spec §"Scanner Grouping
/// Strategies" for the receiver side.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub enum Relation {
    /// No cross-coin binding emitted. Each coin's spend stands alone (signature
    /// aggregation still prevents partial-bundle replay at the BLS layer).
    /// Suitable for single-coin bundles and for multi-coin bundles that don't
    /// require atomic-replay protection beyond the signature aggregate.
    None,

    /// Emit a closed cycle of `ASSERT_CONCURRENT_SPEND` (opcode 64) conditions
    /// across every non-ephemeral coin spend in the bundle: coin 0 asserts
    /// coin N-1's coin_id, and coin i (for i ≥ 1) asserts coin i-1's coin_id.
    /// This forms a single strongly connected component spanning all bound
    /// coins, defending against third-party "pollution" assertions that point
    /// at a victim's coin (the polluter's coin sits in its own trivial SCC).
    ///
    /// **Load-bearing for CHIP-0057 multi-input silent payment detection.**
    /// Wallets emitting `SilentPaymentSend` actions across 2+ XCH inputs MUST
    /// pass this variant to [`Spends::finish_with_silent_payment_keys`]; the
    /// method returns `Err(DriverError::SilentPaymentRequiresInputBinding)`
    /// otherwise. Refactoring this emission shape away from the closed cycle
    /// will silently break SP scanner detection for cross-derivation-index
    /// multi-input sends — the pinning test in `action_system/spends.rs`
    /// guards against accidental drift.
    AssertConcurrent,
}
```

### 6c. Pinning test location

There is no existing `mod tests` in `relation.rs` or `spends.rs`. The pinning test belongs in `action_system/spends.rs` adjacent to `emit_relation`'s implementation (line 338). Add a new `#[cfg(test)] mod tests` block at the end of the file.

The test must:
- Call `Spends::new(...)`, add N coins via `Spends::add(...)`, apply some action so each coin has a `ConditionsSpend`
- Call `prepare(ctx, deltas, Relation::AssertConcurrent)` → returns `Spends<Finished>`
- Walk `finished.xch.items` and for each item:
  - Confirm exactly one `AssertCoinAnnouncement` condition referencing the predecessor coin's `coin_id` (or use `AssertConcurrentSpend` — verify which opcode `emit_relation` actually emits; based on `assert_concurrent_spend(...)` call on line 354, it's opcode 64 `AssertConcurrentSpend`)
- Parameterize for N=2, N=3, N=4

The test does NOT need `chip-0057` feature gate — `Relation::AssertConcurrent` is not feature-gated. (Pitfall E.)

**Verification:** `emit_relation` body at `spends.rs:351-361` uses `.assert_concurrent_spend(...)` — confirming opcode 64 (`AssertConcurrentSpend`), matching the CHIP-0057 Pass 2b spec.

### 6d. What the test asserts

For N coins added in order `[c0, c1, c2, ...c_{N-1}]`:
- `c0`'s conditions contain `AssertConcurrentSpend(coin_id = c_{N-1}.coin_id())`
- `ci`'s conditions (for i ≥ 1) contain `AssertConcurrentSpend(coin_id = c_{i-1}.coin_id())`

This is exactly the cycle that produces a single SCC of size N when the scanner builds its directed graph (Pass 2b detection).

## 7. Lex-min vs iteration-order announcer (sanity check)

Plan 04-04's `emit_silent_payment_announcements` used **lex-min** coin_id selection for the announcer choice. The companion `~/silent-payments` Python prototype uses **iteration order** (first coin given). `Relation::AssertConcurrent` uses **iteration order** (coin 0 = first added).

**This difference is invisible to Pass 2b detection.** SCC computation is invariant under graph topology — the cycle's "starting point" is implementation choice, but all N nodes wind up in the same SCC regardless of which coin asserts which. The receiver computes the same SCC partition either way.

The planner does not need to preserve the "lex-min" semantics from Phase 4. After Phase 4.1, the only binding is `Relation::AssertConcurrent`'s iteration-order cycle. Tests like `cross_index_announcement_binding` (which asserted lex-min specifically) are deleted; no test needs to enforce lex-min anymore.

## 10. Plan slicing

Recommended split into **2 plans** per ROADMAP §04.1 anticipation:

| Plan | Title | Closes | Approx scope |
|---|---|---|---|
| **04.1-01** | Drop announcement emission + update affected tests | partial SC1, SC2, SC6 (existing tests still pass) | ~150 lines deleted, ~5 lines edited (Relation::None → AssertConcurrent in multi-input tests; module docstring update) |

**Why this split:**
- 04.1-01 is mostly deletions; can land standalone — after it merges, multi-input SP transactions emit no binding (gate not yet present) and emit no announcements. Multi-input tests must be updated to `AssertConcurrent` simultaneously OR they'll start failing immediately because the BLS aggregate alone doesn't satisfy Pass 2b detection requirements (but tests don't verify Pass 2b, so they actually wouldn't fail — confirm by running tests after the 04.1-01 changes).

  Actually, more precisely: tests passing `Relation::None` to `finish_with_silent_payment_keys` for multi-input cases CURRENTLY succeed because Phase 4 emits opcode 60/61 binding regardless. After 04.1-01, no binding is emitted with `Relation::None`. The tests still pass at the SDK level (round-trip math closes, output PHs match), but the bundle wouldn't be detectable in production. This is correctness-preserving for the test but functionally degrading for any caller using `Relation::None`.

  → **The Plan 04.1-01 must update multi-input tests to `AssertConcurrent` so they reflect intended production usage.** Otherwise the tests pass falsely.

- 04.1-02 adds the gate that makes the requirement enforced. After it lands, calling `finish_with_silent_payment_keys` with `Relation::None` on a multi-input batch errors. This is the second half of the safety property.

**Could be 1 plan:** if the planner judges the scope manageable as a single atomic commit set. But splitting helps with reviewability (deletions vs additions are conceptually distinct).

**Cannot be 3+ plans:** there's no meaningful intermediate state between "announcement emission gone" and "runtime gate active" worth committing separately.

## 11. Pitfalls

### Pitfall A: `multi_party_hard_errors` stays
`multi_party_hard_errors` (in `send_keys.rs::tests`) tests SEND-03 (Spends-level multi-party rejection), not SEND-06. It does NOT reference opcode 60/61. Phase 4.1 must not delete it. (Cited in ROADMAP §04.1 SC6 retest list.)

### Pitfall B: Multi-input tests using `Relation::None` will need updating
The two SEND-05 tests (`multi_output_same_scan_pk_increments_k`, `multi_output_distinct_scan_pks_independent_counters`) and `input_hash_round_trip` use `Relation::None` against multi-input. After Phase 4.1's gate lands (04.1-02), these will fail with `Err(SilentPaymentRequiresInputBinding)`. Plan 04.1-01 should pre-emptively update them to `AssertConcurrent` (which is the production-correct value anyway), so 04.1-02's gate addition is a no-op for them.

`round_trip_matches_derive_one_time_puzzle_hash` uses single-input — unaffected.

### Pitfall C: Don't delete `conditions_ref()` accessor
The accessor is unused after 04.1-01's test deletions but is `pub` and harmless. Removing it expands the change surface beyond the success criteria. Leave it.

### Pitfall D: Rustdoc on `Relation` must NOT be cfg-gated
`Relation` is not feature-gated; only its SP usage is. The rustdoc applies to all consumers of the enum, not just chip-0057 builds. Don't accidentally add `#[cfg(feature = "chip-0057")]` to the docstring or the pinning test.

### Pitfall E: Don't accidentally re-add `Bytes`, `Conditions`, `announcement_id`, or `SpendKind` imports during Plan 04.1-02

### Pitfall F: Don't gate the pinning test on chip-0057
The pinning test on `Relation::AssertConcurrent`'s cycle emission applies to ALL builds. The enum is general-purpose; SP is one consumer. Test in `action_system/spends.rs::tests` should NOT have `#[cfg(feature = "chip-0057")]` on it.
