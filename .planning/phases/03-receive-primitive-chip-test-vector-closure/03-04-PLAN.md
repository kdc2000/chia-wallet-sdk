```rust
                                let labeled_sk = SecretKey::from_bytes(labeled_scalar.as_bytes())
                                    .expect("labeled scalar < r by ScalarField boundary");
                                detected.push(DetectedSpCoin {
                                    coin_id: out.coin_id,
                                    puzzle_hash: out.puzzle_hash,
                                    amount: out.amount,
                                    parent_coin_id: out.parent_coin_id,
                                    onetime_sk: labeled_sk,
                                    k,
                                    label: Some(m),
                                });
                                found = true;
                                break;
                            }
                        }
                    }
                }
            }

            // CHIP §RECV-04 termination rule: break the k loop only when
            // NEITHER unlabeled NOR any labeled candidate matched at this k.
            if !found {
                break;
            }
```

**Notes on implementation:**

- The labeled branch uses `&candidate_pk + label_pk` — PublicKey + PublicKey via `Add` impl. `candidate_pk` is `PublicKey` (owned), `label_pk` is `&PublicKey` (borrowed from `label_map.iter()`). The chia-bls 0.36.1 `Add` impl is `impl Add for &PublicKey { type Output = PublicKey; }` so we need `&candidate_pk + label_pk` (both sides borrowed).
- `ScalarField::from_bytes_raw(base_sk.to_bytes())` — `SecretKey::to_bytes()` returns `[u8; 32]` already < r by construction, so `from_bytes_raw` is correct here (no double-reduction).
- The `generate_label(scan_sk, m)` call resolves to the public reach-through in `chia-sdk-utils/src/silent_payments/mod.rs` (Task 1 just added it).
- The labeled branch's `break` (after a successful labeled push) is critical: it stops iterating `label_map.iter()` after the first labeled match wins for this k. Without it, multiple labels could double-detect.
- For the `bespoke_k1_detection` test: the in-test fallback derivation (compute_shared_secret + derive_output_tweak + derive_onetime_pk + puzzle_hash_for_pk inside the test body) IS weaker than pinned hex, but the executor can upgrade to pinned hex by running the Python one-liner from the doc-comment. - For the `unlabeled_preferred_over_labeled_at_same_k` test: the assertion is that when the unlabeled branch matches, the labeled branch does NOT run (no double-detection).
